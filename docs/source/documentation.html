How to read this document

This is written before any code, so it is a specification and plan, not a report. Clause numbers in rust (for example SRS 20.1.2 or FRS 7.6.7) point to the two RDSO documents listed in the appendix; every number SignalSafe enforces is traced to one of them. Items tagged MVP are committed for v1. v2 and Later items are planned but not promised.

01 · Project overview

A Kavach test lab that fits in a browser tab

SignalSafe is a software twin of the reference test facility RDSO describes for Kavach. A user lays out a station yard, places signals, points, RFID tags and radio towers, runs simulated locos through it, and injects faults: radio loss, a missed tag, a GPS failure, a signal flickering on the approach. SignalSafe then checks each response against the SRS and explains the chain of events.

The problem

  • Kavach function testing needs a physical bench: real SVK and OVK racks, relay adapters for field inputs, radio and brake simulators. Few people outside OEMs and RDSO ever get to use one.
  • RDSO's July 2026 draft FRS asks for a generic test bench but notes that OEMs don't share common simulator or adapter interfaces, and that "further study is required" FRS 7.6.1.18.
  • The SRS is dense: timeouts, fallback modes and brake rules are spread across 34 sections. Students and new engineers find it hard to see how they combine in a real incident.

Our answer

  • A browser-based bench with the same module breakdown as the FRS: Scenario Editor, Bench Controller, Yard, Loco, Radio, DMI and SMOCIP simulators, Scenario Logger and Evaluation Tool.
  • Reference models of Onboard and Stationary Kavach, written from the SRS, that stand in for the equipment under test.
  • A generic adapter contract, so the same scenarios could one day drive real equipment over serial or Ethernet.
  • An evaluation report that cites the clause behind each pass or fail.

Who it's for

Students and educators in railway signalling and safety-critical systems, who need to see Kavach logic run rather than only read it. Test engineers drafting scenario sequences, which the FRS places in the bench's scope FRS 6.1.1.6. They can prototype and review these sequences before booking time on a hardware bench. Reviewers comparing OEM behaviour against a neutral reading of the SRS.

A test engineer's journey

1 · Build yardTracks, points, signals, TINs, RFID tags, LC gates, towers.
2 · Write scenarioTrains, configs, route timeline, faults, expected observables.
3 · Pre-setLoad config into reference SVK/OVK, power on, register.
4 · RunWatch live: yard, DMI, SMOCIP, radio log. Step, pause, speed up.
5 · EvaluateObservables matched in time and location windows.
6 · ReportPass/fail per clause, causal chain, exportable PDF.

Steps 3–5 follow the simulation phases in FRS 8.2.2: preparation, start and sync, initial communication, scenario run, and simulation stop with event-logger download.

02 · Kavach on one page

The system we simulate

Kavach is Indian Railways' Automatic Train Protection system. Stationary units at stations read signalling state and tell each train how far it may go. Onboard units supervise speed against that authority and brake if the loco pilot doesn't.

Trackside

  • RFID tags, duplicated, on the sleepers. They carry absolute location and TIN, and correct odometry drift (5 m + 5% of distance since the last tag) SRS 3.4.2.4.
  • Stationary Kavach (SVK), a 2-out-of-2 vital computer. It reads interlocking inputs (signals, points, track circuits) and generates movement authority SRS 3.4.4.
  • SMOCIP, the station master's panel with SoS button, health indication and fault codes SRS 3.4.6.
  • Remote Interface Units bring remote signals in over OFC SRS 3.4.7.

Onboard

  • Onboard Kavach (OVK), a 2-out-of-2 vital computer that supervises speed against MA and the brake curve SRS 3.5.2.
  • LP-OCIP (DMI), the driver display with speeds, target distance, mode and soft keys. SoS is sent by pressing SoS + Ack together SRS 3.5.5.
  • BIU, which issues Normal, Full-Service and Emergency brake commands and cuts traction SRS 3.5.6.
  • Two RFID readers, two radios, two pulse generators, all in hot standby.

Operating modes SignalSafe models

Mode names as used in the SRS and FRS. The full transition table is in Annexure A1, which is not in the documents we have. Section 09 explains how we handle that gap.

Full Supervision (FS)Full MA, signal aspect and track profile known. OVK supervises against the full brake curve.
On Sight (OS) · Limited Supervision (LS)Reduced authority. The loco pilot acknowledges the transition with Common/Ack SRS 3.5.5.7.
Staff Responsible (SR)The degraded fallback, e.g. after GPS time-out SRS 20.3.5 or loss of the TSRMS, adjacent-SVK or EI link SRS 20.8.
Trip · Post Trip · OverrideEntered after passing an EOA. Post-Trip and Override are selected on the DMI FRS 7.6.1.12.
Standby · Isolation · Non-LeadingNot supervising, BIU isolated, or trailing loco. No LC auto-whistle in these modes SRS 15.7.
System Failure (SF)Safe state after a vital failure: both RFID readers, PG mismatch, active DMI, brake feedback, or GPS + RTC SRS 20.2–20.6.
03 · What we'll build

Beyond the FRS

  • Adjacent SVK simulator: up to six neighbours for handover tests FRS 7.4.9.3. v2
  • Causal "why" view: every log event records the event that caused it, so a failed observable can be traced back to the injected fault. MVP
  • Replay: any run can be replayed exactly from its seed and inputs. MVP

Explicitly out of scope

  • Card-level hardware testing, which is also outside the FRS's scope FRS 5.1.1.5.
  • Key-management cryptography. The SIM-based KMS isn't connected to the bench FRS 7.3.10. We simulate session setup but not real keys.
  • Certification. SignalSafe is a learning and pre-validation tool, not an approved facility.

Before every run: the pre-set

The FRS requires the equipment under test to be loaded and configured before a scenario starts FRS 8.1. SignalSafe's Bench Controller does this as an explicit, logged step so nothing is assumed:

SoftwareReference-model version pinned in the run record.
Station configYard, control table, track and gradient profile into REF-SVK.
Train configLoco type, consist, brake parameters, Kavach parameters into REF-OVK.
LinksRIUs and adjacent SVKs declared and known to the bench.
Power-upUnits powered via the power adaptor, then the scenario clock starts.

Anatomy of a scenario

A scenario is the bench's basic unit FRS 8.2.1. Each SignalSafe scenario holds the four parts the FRS lists, plus two of our own:

  • Test sequence: signalling inputs, timing, configuration.
  • Track description: conditions and gradient profile.
  • Train description: formation, loco type, rolling stock.
  • Simulation details: which modules run, with what options.
  • Faults and expected observables (SignalSafe additions).

The FRS puts combining test cases into sequences inside the bench's scope FRS 6.1.1.6. The TSE supports this directly:

  • Scenarios can be chained: the end state of one (train position, mode, registration) becomes the start of the next.
  • A sequence such as "enter territory → register → SPAD approach → radio loss → recovery" runs as one continuous simulation with one combined report.
  • The live checks run across the whole sequence, not just each part.
04 · The scenario library

Twelve scenarios, each tied to a clause

RDSO's official test cases (SIF 0533 v4.22) aren't in the documents we have. So the v1 library is our own: twelve scenarios written directly from SRS clauses, each with a setup, a trigger, and pass criteria the Evaluation Tool can check automatically.

S01 Stop short of a red

SIL-4SRS 12 · 3.5.7.1

Loco approaches home signal S1 at ON. The loco pilot (DMI auto-player) keeps notching up.

Pass OVK brakes on the curve and stops short of S1: within 5 m in ≥90% of 200 seeded runs, within 30 m in ≥98%.

S02 Conflicting route inputs

SIL-4SRS 12.1

The yard shows S4 OFF while the point for that route is not detected.

Pass SVK sends the most restrictive aspect for S4 and shortens the MA. No FS MA past S4.

S03 Head-on in block section

Non-SILSRS 14.2 · 14.7

Two locos on TIN 201, approaching each other, both registered with SVK-A.

Pass SVK issues loco-specific SoS to both. Both brake immediately. Brakes release at 0 km/h 14.4.

S04 Rear-end following

Non-SILSRS 14.3

A faster loco closes on a slower one, same TIN, same direction.

Pass Only the rear loco brakes and stops ≥300 m behind. The front loco never brakes and its DMI never shows the alert.

S05 Radio goes silent

SIL-4SRS 20.1 · 5.1

RMS drops all SVK→OVK packets from t = 40 s in an Absolute Block Section.

Pass At 6 s the aspect blanks but FS continues. At 30 s radio failure is declared and the pilot is asked to acknowledge. With no Ack within 15 s, FSB is applied.

S06 One radio dies

AvailabilitySRS 20.1.4

Radio 1 of the OVK fails in mid-section. Radio 2 stays healthy.

Pass The fault is logged and an NMS message is queued. Supervision continues normally, with no mode change and no brakes.

S07 Missing tags vs. a wrong tag

SIL-4SRS 3.5.4.6 · 19.6

Run A: both tags of an expected pair are dropped. Run B: an unlinked tag is planted on the route.

Pass A: "tag missing" shown on the DMI after the L_doubt window, with no brakes. B: brakes on reading the unexpected tag.

S08 Roll back on a gradient

Non-SILSRS 13.1

Loco stopped on a rising gradient with brakes released. It rolls opposite to the cab direction.

Pass Brake and audio-visual warning once roll-back exceeds 5 m. The intervention is shown on the DMI.

S09 Pulse-generator mismatch

SIL-4SRS 20.5 · 6.5

PG-2 under-reads so the two PG speeds differ by more than 5 km/h for a full frame cycle.

Pass OVK goes to System Failure, logs the fault and queues an NMS alert.

S10 Signal flicker on approach

SIL-4SRS 18.8 · 5.2

S4's ECR input chatters OFF→ON→OFF within 1 s while the train is 1.2 km out.

Pass SVK holds the MA for 2–5 s (configured value) and never sends an MA longer than the most restrictive state seen.

S11 LC gate auto-whistle

Non-SILSRS 15.3–15.9

Approach to LC 42-A, in three variants: normal, MA ending short of the gate, and stopped at 400 m.

Pass Normal: continuous horn from 600 m to the gate. No horn when the MA is short of the gate or the train is at standstill. Ack alone cancels it.

S12 Odometry jump

Non-SILSRS 20.7

The OVK's reported distance jumps 150 m between two position reports, inconsistent with its live speed.

Pass SVK detects the error beyond its 120 m default tolerance and sends a loco-specific SoS.

The SIL levels shown are those the SRS assigns to the function under test. They describe the real system, not SignalSafe. Thresholds marked "configurable" in the SRS are scenario parameters in SignalSafe, with the SRS default pre-filled.

05 · Faults & evaluation

What we can break, and how we judge it

A fault is a scheduled change to one bench module, triggered by time, location or another event. SignalSafe never alters the reference models' logic to cause a fault. It only changes what they see through their interfaces, just as a hardware bench would.

RFID (RFID-S)One tag of a pair missing, both missing, data mismatch in a pair, unexpected tag, one reader failed, both failedLog or DMI only for misses. Brake on unexpected tag 19.6. SF if both readers fail 20.2.
YardSignal flicker, point not detected, track circuit stuck occupied, LSS OFF without line clearMA held 2–5 s 18.8. Most restrictive aspect 12.1. Train-length abort after 3 min 8.1.6.

How the Evaluation Tool decides

Following FRS 7.6.15, each scenario lists expected observables. An observable is an event type with filters plus a window in time, location, or both. After the run, the TET searches the combined log (TSL plus both units' event loggers) for each observable in order. A matched record is consumed, so the same brake event can't satisfy two steps. A step can depend on an earlier one, e.g. "within 15 s after the radio-failure prompt".

Results are Pass, Fail (observable missing or outside its window) or Unexpected (a safety event that no step asked for, such as an EB nobody expected).

  { id: 'blank', event: 'DMI_ASPECT_BLANK',

    at: { after: 'blank', sec: [0, 1] } },
  { id: 'rfail', event: 'RADIO_FAILURE',
    at: { after: 'fault:radio', sec: [30, 32] } },
  { id: 'fsb', event: 'BRAKE_CMD', level: 'FSB',

The causal chain

Every event the reference models emit carries a causedBy list naming the inputs or earlier events that triggered it. The report turns this into a readable chain. It is built directly from the log, not generated by AI, so it is exact and reproducible:

t 40.0 s · faultRMS drops SVK→OVK packets
t 46.0 s · 20.1.26 s silent → aspect blank, FS kept
t 70.0 s · 20.1.130 s with no packet → radio failure
t 70.0 s · 20.1.3Degraded mode, Ack requested
t 85.0 s · 20.1.3No Ack in 15 s → FSB applied

07 · Tech stack

Browser-first, engine-centred

The simulation engine is the product, and the UI is a window onto it. So the engine is plain TypeScript with no UI dependencies, runs in a Web Worker, and is tested on its own. Everything runs client-side, so v1 deploys as a static site.

LayerChoiceWhy
LanguageTypeScript (strict)Packet layouts, modes and events become types. Most protocol mistakes are caught at compile time.
FrontendReact 19 + ViteFast dev loop, and the same stack as our previous projects.
Yard renderingSVG (editor) · Canvas 2D (live run)SVG gives crisp, selectable elements for editing. Canvas keeps live runs smooth with many trains and fast-forward.
EnginePure TS in a Web WorkerDeterministic fixed-tick loop off the main thread. The UI receives state snapshots and log batches.
StateZustandSmall and explicit. Engine snapshots replace whole slices, so there's no hidden mutation.
ValidationZod schemasScenario files and adapter messages are validated at every boundary.
StorageIndexedDB (Dexie) · JSON import/exportScenario library and run logs stay in the browser. Scenarios are shareable as .signalsafe.json files.
ChartsRechartsSpeed and distance plots with the brake curve overlaid in reports.
ReportsPrint-styled HTML → PDFThe same approach as this document, so reports match the house style.
TestingVitest · fast-check · PlaywrightUnit tests per clause, property tests on safety invariants, end-to-end tests that run the twelve scenarios.
HostingStatic (Vercel / GitHub Pages)No server for v1. A backend arrives only with the shared library (section 11).

Why not a game engine or a backend simulation?

Unity or Godot would give nicer 3D, but SignalSafe is about logic and timing, not looks, and a browser tab is the lowest barrier for students. Running the engine server-side would make runs depend on network latency. That's acceptable for a dashboard but wrong for a tool that checks 2-second frame timing. A worker on the user's machine keeps every run exact.

Timing model

  • Fixed tick of 100 ms simulated time. Dynamics, odometry and tag detection update every tick.
  • Radio frame of 2 s = 20 ticks SRS 17.11. Each unit gets a slot in the frame. SVK and OVK packets carry frame numbers, and stale ones are discarded 17.12.
  • Logging every 2 s plus on events SRS 21.2, with time and location stamps.
  • Runs go step-by-step, real time, or up to ×20. Simulated time is independent of wall-clock time, so results never depend on machine speed.

Tag detection at speed

At 200 km/h a train covers 5.6 m per 100 ms tick, more than the reader's ≤750 mm horizontal range SRS 3.5.4.3. So RFID-S doesn't sample position. Each tick it checks whether the antenna's path crossed a tag between the last position and this one. This gives no accidental misses at any speed, as FRS 7.6.6.3 requires.

09 · Engineering principles

Built the way a safety tool should be

1 · Deterministic, always

Same scenario + same seed = the same log, byte for byte. All randomness (packet loss, tag jitter) comes from one seeded generator, and nothing reads the wall clock. A failing run can always be replayed and debugged.

2 · Most restrictive wins

The reference models apply the SRS rule that, when several situations overlap, the most restrictive one governs SRS 19.1–19.3. When information stops, the last brake curve continues 19.4. Unknown inputs default to the safe state.

3 · Invariants as tests

Property tests generate thousands of random yards and fault mixes and assert invariants on every tick. Examples: an FS MA never extends past a signal at ON. The front train in a rear-end case never brakes. A brake command is never weakened while its cause still holds.

4 · One clause, one test

Each SRS number SignalSafe enforces (6 s, 30 s, 15 s, 300 m, 5 m, 600 m, 5 km/h, 120 m…) lives in one config file with its clause reference and has at least one unit test. The appendix traceability table is generated from that file.

Honest limits

  • Not an approved test facility. The FRS requires the real bench to be calibrated per Railway procedures FRS 8.1.1.2. SignalSafe has no such standing and its output is not evidence of compliance.
  • Reference models are our reading of the public SRS. They are not any OEM's implementation and are not SIL-rated.
  • Several annexures aren't in our sources. These are A1 (mode transitions), B (DMI layout), C (radio protocol and time slots), D (tag data format) and O (braking algorithm). In v1 those parts use simplified stand-ins, each labelled stand-in in the UI and in reports, so nobody mistakes them for the specification.
  • The braking model is simplified: constant deceleration per brake level with a gradient term, until Annexure O is available.

Definition of done for v1

  • All twelve scenarios pass, and each fails in the expected way when its reference-model rule is deliberately broken (mutation check).

11 · Future features

What could come after v1

Annexure-accurate models Next

Replace the stand-ins with A1, C, D and O once those annexures are available. Packet-level radio framing per Annexure C would let SignalSafe produce byte-accurate packets.

Hardware bridge Research

A small Node or Rust service that maps the adapter contract to RS-232/485 and Ethernet, which most bench interfaces use FRS 7.6.1.17. The same scenarios could then drive real equipment. This needs OEM cooperation, as the FRS itself notes.

SIF 0533 import Next

If RDSO's official function test cases become available, import them into the TSE database as the FRS intends FRS 7.6.2.2, alongside our own twelve.

Adjacent-station handover Next

Full SVK-to-SVK soft handover per Annexure P, with up to six neighbours and shared border tags.

Shared scenario library Later

A small backend (Node + Postgres) for publishing scenarios and reports, with reviewer comments on individual observables.

Classroom mode Later

Instructors assign scenarios. Students predict the outcome before running ("will S05 brake, and when?"), then compare their prediction with the causal chain.

Plain-language explainer Later

An optional assistant that reads the causal chain and the cited clauses and answers questions like "why didn't the front train brake?". It is limited to the run log and the SRS text, and always shows its sources.

NMS & TSRMS views Later

A Network Monitoring System panel showing the queued NMS messages already modelled, and a TSRMS simulator for issuing temporary speed restrictions during a run.

Design language: "Signal Box"

One visual identity throughout, drawn from vintage railway print: olive and sage greens on parchment, rust for anything that needs attention, and brass hairlines with ring-and-dot ornaments. Torn-paper edges separate scenes. Type is Bodoni Moda for display, Manrope for reading and JetBrains Mono for clause numbers, packet fields and timings. Signal colours () are reserved for real signal aspects and pass/fail states, never for decoration.
